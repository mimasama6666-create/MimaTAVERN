# 咪嘛馆原生记忆系统独立审计（2026-10-12）

**结论：实有存储与提示词注入能力，但用户报告的阻塞有明确程序性根因；高失败率的真实原因尚缺 API 侧原始诊断，必须进一步观测和复现。** 不能直接归因于上游，也不能把 memoryTask 独立 AbortController 视作已做到“后台不妨碍聊天”。本文是只读审计，无生产源码修改、无用户真实 API 调用，未验证 Windows、Chromium 点击或用户账号上的具体 provider。

## 样本和版本锁定

- 用户当前运行的是 PNG 导入版，可能 v1.3.9 或 v1.4.0（不能仅凭描述判定）；二者 `app.js` 都有同一阻塞提示逻辑；v1.4.0 `app.js:909`。
- 施工最新版：`咪嘛馆_R1-R5_独立监工返工_完整源码安装包_20261011.zip`。逐字节 `cmp`：其 `app.js`、`standalone-core.js`、`local-store.js`、`novel-memory.js`、`novel-engine.js` **均与 v1.4.0 完全相同**。因此 R1–R5 新包并没有修复原生记忆模块。
- 原生记忆的测试文件 `tests/smoke-v1.3.9-png-memory.js` 和 `tests/smoke-v1.3.9-memory-facts.js` 均离线 PASS；这些测试验证原始数据保存保护，未验证真实 API 性能、前端 UI 可用性及记忆实际回答质量。

## 症状 → 第一个非法状态 → 传播 → 用户结果

### N0（P0）记忆运行期间主动禁止聊天，根因已确定

`app.js:909` 在 `triggerChat()` 的 API 请求之前：`if(memoryTask?.sessionId===currentSessionId)return toast('当前剧情的记忆总结正在进行，请完成或停止后再生成剧情。');`。同一剧情只要内存中有任务（成功/失败结算前），发送按钮不会继续执行。`app.js:594–607` 还把记忆生成和 `isGenerating` 互相作为门槛。进度条不是原因；它只是这种人为互斥的可见表现。`fetchStory()` 在 `app.js:85–100` 有不同 AbortController，只能说明取消所有权已分离，不能推导可并发。**验收必须实测打开摘要后不退出页面即可连续多轮剧情发送；由原生 Speech Turn 拥有生成/发送/结算优先权。**

### N1（P0/P1）摘要过慢：工作量随原文长度与轮次线性/分段增加

`standalone-core.js:665–680`：事实摘要 `splitTextBlocks(sourceText,28000)` 串行遍历后逐个 `await callModel(...,{streamOverride:false})`，超长分段再发 merge；`703–734` 每个轮次区间顺序调用 summarizeFactText，最后才保存所有生成的事实段。

`735–774`：核心记忆 `splitTextBlocks(source,30000)`，若多段则每段模型调用，再多发一次 final merge；单段则一次终稿 API 调用。核心来自全文时每次重读全量原文，而非先用具有完整覆盖和有效来源校验的增量记忆路线。每个 `await` 阶段的真实时长由用户网络、模型、tokens 和请求数量共同影响。本地源码能证明多次调用，**不能仅凭源码证明实际端到端要等几分钟**。

每段失败令整次生成中止，且合并结果未在单阶段 checkpoint 持久保存，旧记忆受保护但用户易反复重付前面已成功调用的成本。不能通过删上下文/增加假摘要/自动换模型“修”。

### N2（P0）自动 Rolling Summary 仍在剧情主请求的同步关键路径

`standalone-core.js:804–833`：`processStoryTurn()` 保存玩家消息后，必须 `await refreshSummary(session,temp,signal,progress)`，然后才组装 prompt 请求正文。`785–801` 的 `refreshSummary()` 一旦历史超过窗口需要更新，就调用另一次模型生成；失败 catch 仅打印 `console.warn` 并跳过，缺少持久 degraded 记录。虽有“失败仍继续剧情”，**但模型响应期间仍阻塞正常回复**；且主请求使用同一个 AbortSignal，辅助总结可能消耗主回合预算。应重排到独立、低优先后台结算，与记忆覆盖区间的可追溯处理配套。

### N3（P0）“API 失败/空文本”不能不经诊断直接甩锅上游

`standalone-core.js:488–516` 中记忆调用与剧情共用 OpenAI-compatible HTTP 构造器；记忆强制 `streamOverride:false`，默认 `model` 来自当前配置，`sendTemperature` 默认开启（除非用户关闭），`max_tokens` 使用用户配置。HTTP 400/429/5xx 按 status 包装；200 JSON 的 `choices[0].message.content` 空文本，报 `E_API_EMPTY_REPLY`。`extractReply` 有 content/text/refusal 等分支，对含其他非标准多模态/推理-only/扩展结构的响应可能解释不足；读取到仅 `reasoning_content` 不应被当有效摘要。错误消息缺乏 jobId、request stage、payload shape、response shape、finish_reason、最大输出配置及真正的输出长度等成套可观测诊断，不能确定用户遇到的究竟是配额、模型参数、返回格式、finish_reason、空内容还是保存 CAS 失败。其缺失本身构成诊断契约缺口。

### N4（P1）记忆**并非**完全摆设，但效果仍缺证明

`standalone-core.js:295–300` `buildSystemPrompt` **确实**读取 `normalizeManualMemory(session.manualMemory)`，若 `injectCore/injectFacts` 开启，将核心记忆和最近 `factInjectionLimit` 个事实摘要加入 System Prompt。`:325–326` 组装完成后把这些 sections 放进 preview。因此有“存储→下轮提示词注入”的真实链路，并不是假按钮。

离线独立 mock 路由验证：存入 `core/facts` 后 `prompt-preview` 的 `sections` 具有 `manual_core_memory` / `manual_fact_memories`；关闭两个开关后立即不再存在；HTTP200 空 `content`、reasoning-only 和 HTTP400 模拟分别返回 `E_API_EMPTY_REPLY`、`E_API_EMPTY_REPLY`、`E_API_HTTP_400`，之前的核心内容未被覆盖。测试不调用外部网络。

局限：不是语义检索，仅将 core 全文、按 endRound 排序的最后 N 段 facts 放入系统提示。rollingSummary、pinnedFacts、core 和 facts 可能重复甚至有过期冲突；没有严格的事实版本验证、实时查证、相关性召回和可观察正确率。因此只能称“可以把已有摘要喂进模型”，不能保证“模型正确记住、随时检索”。这些属于需要按实际能力逐步扩展的增强任务，不能因缺少向量检索就删掉现有注入。

### N5（P1）并发保护有基础，但不足以作为完整任务服务

`standalone-core.js:685–702` 的 `commitMemoryIntoLatest` 在保存前重新读取 `getSession` 并验证历史前缀、同类记忆未被手工修改；`733/774` 再 `saveSession`，结合 `local-store.js` CAS 可以保护一部分同页面/并发修改。现有测试覆盖“总结途中追加消息不会丢”和“手改核心记忆不被迟到回复覆盖”。但任务对象 `app.js:569–592` 仅保存在浏览器内存 `memoryTask`，页面重新加载后无法拿回尚未完成的请求和中间候选；缺少 durable jobId、attemptId、stage checkpoint 与恢复/回滚用户界面。也未有多 Tab 浏览器真测。**应保留已经正确的前缀保护，不得降级为简单全量覆盖。**

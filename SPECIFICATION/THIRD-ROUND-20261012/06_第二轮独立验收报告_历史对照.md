## 新发现：P0/P1 缺陷（按“首个错误状态 → 传播 → 可见后果”）

### P0-1：聊天进行中修改 CSS/资源会让已生成回复丢失、pending 卡住【独立模拟已复现】

- 相关文件：`compat-runtime.js:156–189`、`:237–251`，`compat-ui.js:58–59`，`compat-store.js:47–48`。
- 第一错误状态：`beginTurn` 把当前通用 `session.revision` 记录为 `t.sessionRevision`；同一 `compat_sessions` 记录既是**外观/挂载配置**又是**生成结算门槛**。普通 `styleResourceId` 切换使用 `putCAS` 推进同一修订号。
- 传播：`finishTurn` 要求 `s.revision===t.sessionRevision`，不满足时 **静默不写任何 settlement**（事务正常完成），即使模型返回合法文本。`dispatch` 随后检测 journal 不是 committed 而报错；catch 再次以旧修订尝试结算仍 no-op。
- 复现：在正在 pending 的 turn 上模拟启用 CSS，调用 `finishTurn(...,'real provider answer')` 后取得 `{"journal":"pending","pendingTurnId":"turn-5","unchangedReply":true}`。
- 用户后果：生成可能已经消耗 API 而无角色回复，发送栏后续卡在存在未结算回合。切换世界书、挂载资源等更新同一 session revision 的操作同样存在风险。
- 根治建议：隔离 speech-turn 结算权威与可见外观的 revision；结算验证 stable `turnId/attemptId/pendingTurnId` 和必要的 payload/config snapshot，不用通用展示修订作为旧回复 fence。允许外观改变不会杀主回合。资源行为若要延迟生效，则在准入时冻结生效快照、在下一回合使用。增加同真实 IndexedDB transaction 的并发回归，验证完整回复真正出现。

### P1-1：外部挂载 CSS UI 显示启用，实际消息 Shadow DOM 不加载【明确调用链缺口】

- `compat-runtime.js:90–107,125–139` 允许挂载外部 CSS 并将其加入 `resourcesFor`；`compat-ui.js:58` `mountStyle` 允许“来源是本卡 **或** 在 mountGraph 中”的 CSS。
- 但 `compat-ui.js:56` 实际构造 `#compat-messages` Shadow DOM 时，仅在 `style.sourceId===session.sourceId` 才追加 CSS 内容。外部来源的 `styleResourceId` 不满足，`cssSafe`/样式注入根本不执行。
- 这是挂载成功但实际演出不生效的假阳性；应在渲染落点重用经过校验的有效挂载图，并核实撤销后失效、切换剧情不串色，未经验证 CSS 仍要限制作用域。

### P1-2：用户已终止的迟到回合，被错误向插件广播 turn.failed【独立模拟已复现】

- `compat-runtime.js:245–251`：正确拒绝 stale reply 之后，在 catch 无条件调用 `finishTurn(...null...)` 并 `notifyPlugins('turn.failed')`，不检查最新最终 settlement。
- 模拟中主 journal 的结果 **`aborted`**，但插件事件得到 `turn.failed`；输出：`{"actualSettlement":"aborted","lateErrorCode":"E_CANONICAL_CONFLICT","events":[{"name":"turn.failed","turnId":"turn-5"}]}`。
- 未来有状态栏、插件脚本、音声事件时会出现错误事件或重复效果。应只有真正完成 `pending→failed` 转移的唯一结算点才发失败事件；abort、旧 attempt、迟到重复完成均不应发 failed，事件要以可幂等 ledger/ID 持久追踪。真实结果失败的恢复也要能区分“生成失败”与“被另一回合覆盖”。

### P1-3：正则隔离虽然不锁 UI，但每条历史消息串行新建 Worker，长剧情明显降速【独立基准复现】

- `compat-runtime.js:140–150` 对整条 prompt 消息列表逐条 `await isolate.apply()`；`compat-regex-isolation.js:12–27` 每调用一次创建并销毁 Worker。`send` 先 `preview` 后 `dispatch`，意味着正常发送最少执行两遍历史正则处理。
- 本机独立 Node 基准：20 条常规消息约 842ms，100 条约 4859ms，只计算一次正则处理，**不含模型响应时间**。实际历史百条时两遍可能近 10 秒；不同机器有所差异。
- 不能通过删 History、缩短角色设定或关闭正则“优化”。应将一轮完整 prompt/display 的规则序列在同一可终止 Worker 批量处理，并缓存带 canonical message revision/rule hash/phase 的安全派生视图，同时守住整体执行预算、回合优先级和精确语义。缓存不应替代原始消息。

- **R3**：prompt/display 基础正则已经隔离，MVU 变量 checkpoint 与动态状态栏、正则高级替换和完整 CSS 演出未完成。
- **R4**：可终止 Worker 自定义 SDK 可用于有限按钮/变量/消息/事件。第三方 Tavern Helper 完整 API、原生 DOM 操作或手机播放器完整演出不可当作兼容成功；iframe/opaque-origin/CSP 真正恶意样本浏览器验收尚未完成。

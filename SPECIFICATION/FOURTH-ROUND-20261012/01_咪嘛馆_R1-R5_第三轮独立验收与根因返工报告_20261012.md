## P0-1：未摘要历史无限增长进入正常剧情 Prompt

- **首个不受限状态**：`standalone-core.js` `assemble()` 中 `needsRawGap` 为真时，以 `new Set(session.messages.slice(coverageStart))` 将全部未覆盖旧消息加入 `historyForPrompt`，绕过 `recentMessageLimit`，没有对实际可发送上下文预算和上游模型窗口的限制/拒绝保护。
- **传播**：后台记忆失败或长期等待 → backlog 增大 → 每轮主剧情 `assemble` 带入整段旧历史 → API 请求过大、429/400/context exceeded 或严重延迟 → 进一步恶化后台与正常回复。
- **独立复现**：`long_prompt_probe.js` 纯本地 Core/假 IDB；固定最近窗口 12，30/100/200/500 轮，实际组装 60/200/400/1000 条历史，估算 Tokens 12,306 / 39,886 / 79,286 / 197,486；该 token 数是咪嘛馆源码估算，不是官方 tokenizer 或真实计费。
- **严重级别 P0**：不再静默抛弃旧原文是正确方向，但不能通过无上限输入把主剧情拖死。
- **必须修**：全部原始 History 保留在持久化 Store；建立滚动摘要分段 source coverage 与可恢复 checkpoint、基于模型真实预算的组装验证/可追溯检索，待总结区间不能静默缺失。无法在有限上下文满足该轮知识需求时明确报告缺口、支持恢复原任务；不能用删 History、永久摘要替代源或任意裁掉原文来通过验收。测试 50/200/500+ 轮，故意让 memory API 429、崩溃、网络拒绝，仍验证 Direct Reply 可预测且数据不丢。

## P0-2：普通正文中的 Provider 拒绝模板可污染长期记忆

- **首个错误状态**：`memoryModel()` 以 `callModel()` 返回非空字符串作为有效长期事实候选。`extractReply` 只可识别结构化 refusal，无法识别 API 返回 `choices[0].message.content` 里的普通拒绝文本，不执行结构化记忆候选契约验证。
- **传播**：HTTP 200 返回 `I am sorry, but I cannot assist with that request.` → `/memory/core` 视作成功 → `commitMemoryJob` 写入 core → `buildSystemPrompt` 下一轮注入这段拒绝模板。
- **独立复现**：`memory_bad_output_probe.js`（本地假 IDB/mock fetch，100%复现），输出 `{"success":true,"storedCore":"I am sorry, but I cannot assist with that request.","injectsRefusal":true}`。
- **必须修**：在候选进入 canonical 之前做任务级 output contract 验证（结构化内容、有效事实/来源、拒绝/控制文本、截断、占位、意外 system 文本），失败记录诊断并保留原 core/facts；不可只用一条英文黑名单误杀真正的剧情台词。明确区分“模型成功返回字符串”“有效记忆候选”“事务保存成功”“后续实际注入”。对事实/core/rolling 三条路径均要覆盖。

## P1-1：滚动记忆后台结算测试时序不稳定

- 第一次运行 36 个 smoke 脚本：35 PASS，`tests/smoke-third-memory-journal.js` 于第 58 行 FAIL（预期 committed，实际 running）。
- 相同脚本在同一环境单独循环 20 次：18 PASS / 2 FAIL，失败位置一致；加了调试输出的同构副本循环 30 次全部通过，表明时序敏感，不足以判断真实浏览器生产根因。
- 目前测试以 80 次 × 5ms 轮询等待，模拟 IDB 使用 `setImmediate` 调度。必须记录停留 stage、写入开始/完成/transaction aborted、pending request/attempt；改为可观察 settlement promise/明确生命周期触发而非延长 sleep，复核真实 Chromium IndexedDB 和多标签，不能把测试绿灯当根因已消失。

## P1-2：刷新后后台 Rolling 的运行状态需人工接管

`beginMemoryJob` 对原 journal `status==='running'` 报 `E_MEMORY_JOB_PENDING`；`refreshDurableMemoryJobs` UI 允许人工确认失效，`resumeMemoryJob('rolling')` 在 interrupt 之后不立即恢复，而等待下一轮正文重新调度。异常关闭、离线等情形下无人处理可能形成长期债务。必须区分同标签运行/异标签存活/崩溃 orphan，使用稳定租约和 attempt fencing 自动安全恢复原任务；在不确认旧 attempt 已失效前不得并发写入，且不得阻断 Speech Turn。必须真实测试关闭 Tab、刷新、后台 Worker 异常和重开。

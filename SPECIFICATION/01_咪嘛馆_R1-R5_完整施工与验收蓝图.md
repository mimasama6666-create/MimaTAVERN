# 咪嘛馆 × SillyTavern 生态兼容工程｜R1–R5 FULL-CONTRACT 一次施工蓝图

**版本**：BLUEPRINT-R1-R5/2026-10-11 · **交付性质**：施工设计，不是已经修好的程序 · **项目**：MimaTAVERN（咪嘛馆），**非 MIMAMAO、非 QQBOT**。

> 一句话目标：保留“傻子也能开盖即食”的咪嘛馆原生模式，同时新增可渐进启用、可查看全量来源、可调试、可停用、可导出与回滚的「酒馆兼容实验室」。目标是尽可能保留 SillyTavern 角色卡与生态插件的**实际玩法**，不是把 JSON 字段导入成功伪装为完整兼容。

## 0. 给新对话工作猫的最高指令 / 施工定义

- **R1–R5 在同一工作树、同一轮交包完成**，但必须按 R1 → R2 → R3 → R4 → R5 的依赖顺序开发、逐门槛验收。不能用“R1 做完先交付、以后有空再 R2–R5”取代本次范围；也不能跳过先决条件并宣称全做完。
- **源码是事实**：施工前重新在文件库定位当时最新版，而不是机械以 v1.4.0 覆盖后续更新；若新版本存在，先作差异清单，记录原能力并把本蓝图映射到新调用链。禁止把旧蓝图中的函数行号视作永久有效。
- **验收单位是用户玩法**：从导入 PNG/JSON/CHARX，到检查、选择、挂载、世界书激活、生成、消息显示、状态栏、按钮/音乐、存档/读档、退出兼容模式，必须端到端完成。无真实环境验收的部分明确“未实测”，不准作完全兼容承诺。
- **原生主流程不退化**：原生剧情、模型配置、角色/玩家 Persona、记忆总结、事实/核心记忆、小说、助手、CSS 主题、回滚和旧数据导入导出能力全部保留。不能靠关闭现有功能、缩上下文、删信息、fallback/占位成功、用重试掩盖状态机错误获得测试绿灯。
- **没有支持的生态扩展不得模拟成功**：不能实现 Tavern Helper 某个 API 就谎称支持所有 API。插件兼容采用“实际 API 和效果逐项 PASS”的清单。需要 SillyTavern 原生环境的内容，使用 R5 的官方 sidecar 选项；不将其记作咪嘛馆内部 R4 兼容。
- **不将外来 JS/HTML/CSS 自动赋予本地高权限**。用户导入文件不等于授权运行脚本，不能为了最大兼容让未知脚本拿到咪嘛馆的 IndexedDB、密钥、DOM、文件系统。此原则优先于“看起来一切插件都能跑”。
- **R1–R5 总包一次交付，配套独立 rollback、测试证据、对照报告、README、Windows 启动入口及完整保留原始字节的卡包数据方案**；严禁带入用户私人存档或 API key。

### 0.1 合格的最终定义

最终成品至少能在原生模式保持旧体验，并在兼容工作区做到：① 解析多种酒馆卡和 JSON/CHARX，保留原文/未知字段；② 建立独立剧情并按照可比对的 ST 世界书规则构造 prompt；③ 让适配后的正则、状态栏、CSS、变量真正工作且不污染历史；④ 对受支持的插件按钮/事件/消息读写/音频实际运行并可撤权；⑤ Windows 上可选启动官方 SillyTavern sidecar 运行不支持的原生生态扩展，显式指出哪一套宿主在执行。针对没有接入的任意第三方插件仅做到 L0–L2 也允许，但**报告必须如实列为未完成运行兼容**。

## 2. 术语、能力等级与不得假成功的契约

- `Source Capsule`：原始文件字节、所有 PNG 文本块/扩展、嵌入资产及哈希与 provenance 的**不可变来源包**；不能被规范化器重写。
- `IR (Intermediate Representation)`：用于识别的类型化资源清单，**不是**已经可执行的配置；每项携带来源路径、原始片段、格式与版本、启用状态、字段映射、未知字段。
- `Projection`：从来源包导出到某个目标宿主/特定版本的可运行投影，可重建、有版本、有转换日志；不能代替 Source Capsule。
- `Compat Session`：酒馆兼容实验室新剧情，拥有自己的世界书、prompt、正则、变量、渲染、插件权限、快照与日志；不是旧 Session 改名。
- `Original-host Session`：由独立官方 SillyTavern 运行；咪嘛馆仅管理启动/打开/导入导出边界，不能伪装内嵌自研运行。

| 等级 | 显示给玩家的措辞 | 最低证据 |
|---|---|---|
| L0 发现 | 检测到 | 类型/位置/字节边界成功识别 |
| L1 原文保留 | 可完整查看与导出 | 哈希、内容原样回读、未知字段保留 |
| L2 安全转换 | 可转换并保存 | 转换前后结构校验、差异、完整目标验证 |
| L3 原生兼容运行 | 已验证在咪嘛馆兼容环境可用 | ST 黄金参考输入、触发、prompt、显示/副作用对照 |
| L4 特定插件运行 | 已实测指定插件与版本 | 完整事件/API/权限/DOM/持久化验收 |
| L5 官方宿主运行 | 通过官方 SillyTavern 独立运行 | 目标插件在对应官方宿主真实演示，非咪嘛馆仿真 |

每项兼容状态必须分开记录：`detected`, `preserved`, `converted`, `mounted`, `enabled`, `runtimeVerified`, `unmetDependencies`, `semanticGaps`, `sourceHostVersion`, `targetRuntimeVersion`。不能用单一绿色“兼容成功”替代。

## 3. 产品设计：两个入口，默认永远简单

### 3.1 首页与首次使用

**原生咪嘛馆**：首页仍默认展示现有剧情；保留一键导卡、选择角色、开始聊天，不展示世界书数字枚举、JavaScript、Token 预算等专家术语；以前所有按钮原位可用。

**酒馆兼容实验室（高级玩法）**：旁侧新的「高级 · 酒馆卡 / 插件」入口。首次使用向导仅三步：① 拖入 PNG/JSON/CHARX 或插件包（自动识别）；② 分析展示“角色卡 / 世界书 / 正则 / CSS / 状态栏 / 插件 / 媒体 / 缺失依赖”，用通俗标签：可直接玩、需要确认、有兼容限制、需原版酒馆；③ 选择“快速开始（只用已验证且安全的内容）”或“自定义挂载（高级）”。高级选项折叠，绝不向新手弹出大量技术术语。

**始终有六个直观入口**：「完整内容查看」「查看原始 JSON」「兼容报告」「依赖和授权」「本轮提示词预览」「退出兼容模式」。扫描页面不能因未知字段报错就假装“没有资源”；未识别资源以原样导出。

### 3.2 角色卡体验边界

- 可选择多个开场白、支持按原卡次序切换；但选定后写入独立会话，不把 alternate greeting 追加成多条系统消息。
- 角色卡附属世界书/正则与外置插件显示“绑定至此角色/此卡包”，可在多个 Compat Session 间显式重用；脚本权限按每个角色卡/会话分别授予，不继承到全局。
- 显示实际启用状态与原卡 `enabled/disabled` 区别：`来源原本启用` ≠ `咪嘛馆授权启用`。
- 顶部始终显示运行后端：`咪嘛馆兼容引擎` 或 `原版 SillyTavern`，防止误以为两个环境同一存档。

## 5. 数据安全架构（R1 必做；绝对不准最后补）

### 5.1 两库隔离的默认实施策略

采用独立浏览器 IndexedDB `mimamao_tavern_compat_v1`（名称建议；以施工实际记录为准）。**旧库** `mimamao_tavern_standalone` 的原 `state` 键、schemaVersion=4、已有 export/import 合同全部冻结；不试图塞入新字段，因为旧 `normalizeState()` 会剔除未知顶层属性。新库按对象存储：

| object store | 内容与索引 | 是否可修改 |
|---|---|---|
| `source_capsules` | 文件字节/文本块/格式判定/原始 hash/创建时间；`sha256` 唯一索引 | 不可变；相同哈希只复用，不覆盖 |
| `assets` | 图片、声音、字体及相对路径映射（散列/大小/类型）；引用计数与来源关系 | 内容不可变；引用关系可事务修改 |
| `resource_ir` | type、sourceId/path、adaptedVersion、enabledInSource、unknown 字段与警告 | 重建用新 revision，不覆盖 raw |
| `resource_projections` | 可运行目标投影与 semanticGap、所依赖的 adapterVersion | 以新版本新记录替代，而非改 raw |
| `compat_sessions` | mode、cardId/revision、manifestId、prompt profile、plugin grant binding、会话版本 | CAS version 与不可串台键 |
| `messages` | sessionId、role、raw、modelContent、displayView cache、branch、版本、settlement | 追加为主；有受控 edit 分支版本 |
| `variables` | session/card/script/message namespace，值和 revision | 事务写与权限校验 |
| `grants` | 插件指纹、能力列表、作用域、批准版本、撤销版本 | 默认无权限；撤销保留审计 |
| `events_jobs` | 含稳定 eventId/turnId、幂等 key、执行状态、effect journal | 状态机单权威、可恢复 |
| `import_journal` | scanId、planId、source hash、事务预演与提交记录 | 幂等；失败可确认未写入 |
| `sidecar_links` | 官方宿主版本/安装路径/端口/快照引用（**不存账号令牌**） | 用户显式保存 |

约束：主聊天/小说写旧库，兼容剧情写新库；只能通过**显式、可预览的导入/导出**在两模式间传递资源，不能共享 mutable session state。禁止“用户切到原生页就把 compat 会话拼回旧 sessions 数组”。

### 5.2 事务、CAS、读库错误与版本迁移

- `revision` 在**单个 IndexedDB readwrite transaction** 内比较并提交；跨标签并发对同一资源 CAS 冲突明确暴露，不允许稍后旧任务覆盖较新内容。新库跨 store 事务需同库完成；不能通过多轮分散 `put` 实现虚假的原子性。
- 两个数据库之间没有可依赖的原子分布式事务：所谓“备份所有数据”必须先收集两个库的**一致性快照与各自 revision**，导出一个带 manifest/hash 的外层包，并记录对应版本；若过程中 revision 变化则明确重新尝试快照，不输出自称一致的杂糅结果。
- 跨库恢复先**验包（格式/哈希/对象关系/大小/依赖）→ 备份旧库与新库 → staging + 恢复日志 → 分别提交 → 全部复核**；提交第一个库后第二个库失败时不能谎称原子完成。必须有确定性的 recovery/rollback 计划，至少提供完整版本化备份用于安全回滚；不允许用空结构掩盖失败。
- 浏览器的配额不足、IDB unavailable、private mode、quota、CRC/hash 错误、400/408/429/5xx 网络失败都是“失败/不可验证”，绝不是“没有用户数据”；fail closed/read-only，保护现有 Store。
- 新 schema 要具备 `dbVersion`、`contractRevision`、`migrationId`、upgrade journal。禁止重复 migration 或向下迁移损坏旧档。旧原生 `schemaVersion=4` 不变；若真的改旧库，需提供旧版本备份和严格转换器，不可直接重写历史。
- 并发资源事务不仅检查目标 session，还检查 source manifest、worldbook/regex、adapterVersion 和关联 grant 的 revision，避免旧脚本试图复活已卸载资源。
- 不为了性能把历史永久压缩为总结，不偷减传入模型历史预算；大型资产可**独立 blob/分片与惰性加载**，惰性仅影响 UI/读取，不删除语义与正文。旧 IndexedDB 大对象复制与多标签竞争要有压力测试。

### 5.3 备份与用户安全入口

原有「导出咪嘛馆资料」保持旧格式兼容；新增「导出全部（原生+兼容）」和「仅导出兼容卡包/会话」两条明确路径。每份包记录包契约版本、原始文件哈希、安装兼容引擎版本与 sidecar 版本；默认排除 API key、授权令牌、私人环境路径。支持只读完整性校验、干运行导入、逐项选择恢复和一键回滚。用户安装新版只需覆盖静态前端文件；**不会要求清除 IndexedDB、删除浏览器资料或格式化旧数据**。

## 6. R1｜格式与无损卡包：施工细则

### 6.1 导入识别器 `detect -> decode -> inventory -> validate -> plan -> confirm -> commit`

**不要仅凭扩展名**：读取 magic bytes、MIME、文件头、内容 schema。第一批支持：PNG `chara`/`ccv3`/asset chunks、JSON CCV1/CCV2/CCV3、角色数据只在 data 内的变体、单独世界书 JSON（entries 对象/数组）、SillyTavern 正则 JSON、Chat Completion preset JSON（识别多种结构并把未知原文保留）、含 manifest 的扩展 ZIP、CHARX (`card.json` + assets)；普通 PNG/JPEG/JSON 则说明并非可执行角色卡。

角色卡 V3 的 `ccv3` 优先于 `chara` 是标准推荐；若两者不同则同时保留、显示 diff 和候选优先级，不能丢弃 V2。V3 解析失败时不能假装 V3 成功；若 V2 合法，允许经人工确认选择 V2。处理重复 chunk、PNG 压缩文本、UTF-8/Latin-1 编码、巨量元数据、CRC 错误及未知自定义键。

**CHARX**：root `card.json`，asset path 大小写敏感，规范可能使用 `embeded://`（规范原文拼写），不可擅自自动更正成 `embedded://` 导致资源找不到；容错 alias 需要 provenance 和测试。限制 ZIP 实际解压字节、文件个数、单文件、路径深度与循环引用；杜绝 `../` 和绝对路径、软链/外部路径污染。只从白名单显示格式生成 blob URL 并在卸载时 revoke，不把 JS/HTML 伪装成图片。

**资源列表**区分 `character`, `world_info`, `regex`, `prompt_presets`, `css`, `html_template`, `script_source`, `plugin_bundle`, `quick_reply`, `variable_schema`, `media`, `raw_unknown`；依赖树记录同一资源被哪个条目/脚本引用。JSON 插件必须识别“包含脚本的 JSON”与“可执行 JS 插件仓库/ZIP”不同。

### 6.2 有损转换与用户决策

转换计划每一项标注 `exact`, `conditional`, `unsupported`。只有已通过模板验证的 exact 映射可默认推荐挂载；conditional 显示差异与前提并由用户确认；unsupported 必须保留原文、可导出、不会出现在“已启用”的列表。导入重复源文件按 `(sha256, sourceHost, sourcePath)` 幂等，同文件重新解析不复制 13 条世界书；源相同但目标当前已被玩家手改时提示比较/新增分支，不覆盖。

**原始 Source Capsule 永不被 normalize 替换**：保留原 bytes/base64、元数据块顺序、未知字段、扩展、禁用状态、角色文本和媒体。重新导出原样卡时应可用原字节，导出“已编辑的转换卡”则必须明示重新编码且可能不等价，附 `conversion-report.json`。

### 6.3 R1 验收门槛

- 王爱英 PNG：双 `chara/ccv3` 完整保留、角色数据、13 条世界书、9 条正则、3 个脚本都可查看/导出；不意外执行脚本。另需至少 V1/V2/V3/CHARX/独立 World Info/外置 Regex/外置 preset/ZIP manifest 多样 fixture，且测试**差异化双块**样本。
- malformed JSON/CRC/ZIP bomb/超大文本/未知 asset/路径穿越/重复 uid/Unicode 文件名：不静默丢弃字段、不覆写任何用户数据、错误可定位 `file/path/adapter/stage`。
- 原生角色卡原来 `.txt/.json/.png` 导入仍能工作，旧资源库可正常显示/挂载/导出。

## 7. R2｜独立酒馆 Prompt 与 World Info 运行引擎

### 7.1 Prompt 必须有类型化槽位；不能只有“一段 system 文本”

兼容工作区建立 `PromptSegment {id, sourceId, sourcePath, slot, role, depth, order, priority, content, tokenEstimate, enabled, trace}` 与 `PromptEnvelope {sessionRevision, resourceManifestHash, segments, messages, providerCapabilities, estimatedBudget, warnings}`。默认顺序根据固定的 ST 官方 commit 的具体 prompt manager 和相关枚举对齐：角色描述/性格/场景/示例、system_prompt、post_history_instructions、用户角色、世界书前后位置、作者备注、in-chat depth、outlet、聊天历史与本轮用户输入。**不能先写死万能顺序，再靠少数截图说正常。**

- 保存角色卡中的各种 prompt 字段，不合并丢失信息；宏（`{{char}}`, `{{user}}`, `{{random}}`, `{{roll}}`, `{{outlet::...}}` 等）按 ST 版本逐一支持与测试，不支持必须显示为未替换、可选阻止执行，严禁去掉整段。
- Provider 层复用咪嘛馆现有 OpenAI-compatible 传输能力作为受控适配器，仅共享模型请求管道而非旧 `assemble()`； provider 角色兼容、系统段及顺序能力必须显式记录。真实 payload 预览在发出前与网络请求等价；若发生降级必须指明改变了什么，不能悄悄删 system/developer 或缩少历史。
- 多消息/多身份/深度注入正确落在实际 message 序列；世界书预算按官方激活、优先级、群组/预算淘汰规则计算，日志记录每条激活、未激活、被预算排除原因。

### 7.2 世界书状态机与算法验收

基于指定官方 commit 的 `public/scripts/world-info.js` 与官方 World Info 文档梳理**逐字段枚举表**（不许靠推测）：

1. `keys/key/keysecondary` 主键次键，`selectiveLogic` 4 模式：AND_ANY / AND_ALL / NOT_ANY / NOT_ALL；全词/大小写/正则匹配与扫描来源过滤，正确处理全角/日文/中文关键词。
2. `constant/disable`, `order`, `probability`/`useProbability`, `matchWholeWords`/`caseSensitive`、`scanDepth`, `minActivations`、book selection、角色 lore 与 global lore 顺序、可见 message 范围。
3. Recursive scan：初次匹配、递归内容作为新上下文的影响、`excludeRecursion/preventRecursion/delayUntilRecursion`、递归循环检测、硬约束预算；stable seed 用于 golden test，生产保留可复现随机选择证据。
4. `sticky`, `cooldown`, `delay`：按官方版本真实语义建立会话级 turn counter/canonical source message index；编辑旧消息、再生、删除、重试时不重复推进计数。
5. 群组互斥、weight、優先级；同一书不同条目的插入排序、outlet 宏、depth=0/任意深度、insertion role 与位置。
6. 数字/字符串位置转换：建立来源版本专属 enum map；`after_char` 作为样本变体单独通过证据支持，不要把未知位置强制改 `middle`。未知/冲突位置保留原值并禁止 L3 声明。
7. 先激活再预算与先预算再激活在 ST 版本中的行为须经**同输入双端 reference**比对；一旦与官方实现有偏差，记录语义差异而不是改标准 fixture 迎合自身。

**纯函数接口建议**：

```ts
interface WorldInfoEvaluation {
  matched: Array<{sourceId:string, entryId:string, reason:string, keys:string[], stage:number}>;
  skipped: Array<{entryId:string, reason:string}>;
  inserted: Array<{entryId:string, slot:string, depth:number, role:string, order:number, text:string}>;
  budgetExcluded: Array<{entryId:string, reason:string, tokenEstimate:number}>;
  nextActivationState: object;
  traceId: string;
}
function evaluateWorldInfo(contextSnapshot, sourceEntries, settings, deterministicSeed): WorldInfoEvaluation;
```

**状态更新时点**：`evaluateWorldInfo` 不改变 canonical session。`nextActivationState` 只有通过唯一 Speech Turn settlement 才写入，以避免模型失败/取消时提前扣冷却或触发 sticky。若官方参考在不同场景有特殊时点，以 pinned 版本行为为准并明示差异。

### 7.3 消息主权和发送流水线

`READY → INPUT_RECORDED → PROMPT_PREPARED → REQUEST_IN_FLIGHT → RESPONSE_PARSED → RESPONSE_ADMITTED → CANONICAL_COMMITTED → PRESENTED`；失败走 `FAILED_<stage>`，取消走 `ABORTED`，已 commit 但显示失败走 `PRESENTATION_DEGRADED`（文本仍在）。所有请求带 `turnId, sessionId, sessionRevision, attemptId, provider, model, promptHash, sourceManifestHash`。

输入 `rawContent` 只存用户原文，不被 prompt regex 反写；模型原始 `rawResponse` 与经过角色后处理的 `canonicalContent` 分开；展示 HTML 与正则显示是**可重算投影**。编辑/重生/继续/删除按同一 revision/branch 规则处理，不能让旧模型响应或旧脚本覆盖新回合。保证 Direct Reply 不被插件音频、CSS、识图、变量、状态栏更新等辅助任务阻断；脚本如果声明“生成前必须运行”却缺能力，不可默默跳过继续伪兼容——允许明确拒绝本次高级玩法的生成或要求改用 R5 原版宿主，但原生普通聊天不受影响。

### 7.4 R2 验收

不仅测试最终字符串；针对原版 ST 环境同输入，同 worldbook/预设设置，比较触发条目集、触发顺序、每个注入槽位、role/depth、宏、最终 provider payload（忽略无关 ID 时间戳）。测试 sticky/cooldown/recursion/random seed，在刷新、改剧情、分支、重试、断网后仍可解释和复现。原生剧情 `assemble()` 的黄金快照前后不变。

## 8. R3｜正则、显示、状态栏、CSS、变量与音频资源

### 8.1 与 ST 正则的阶段对齐

把官方 `regex_placement` 版本映射作为引用配置，而非混入现有四阶段。官方 release 枚举示例：`USER_INPUT=1`, `AI_OUTPUT=2`, `SLASH_COMMAND=3`, `WORLD_INFO=5`, `REASONING=6`；`MD_DISPLAY=0` 已标记废弃，版本差异可存在。`placement:[2]` 只表示 AI Output 放置点，不直接代表“只影响显示”。并结合 `markdownOnly`, `promptOnly`, `runOnEdit`, `substituteRegex`, `trimStrings`, min/max depth 等判定实际执行。

分开五种物理文本：`sourceRaw`、`canonicalMessage`、`promptProjection`、`displayProjection`、`runtimeSideEffects`。任何 `displayProjection` 不可写回历史/记忆；任何 `promptProjection` 必须进入实际发出的 payload 才算生效；World Info 正则必须用源相应阶段而不是一概对全消息替换。每条正则按原次序运行、支持 ST 的捕获替换语法并记录差异；潜在 ReDoS 的规则进行静态检测、隔离执行/预算与显式报错，**不吞掉其输出或假装未命中**。对难以保真的复杂表达式可提供不启用与 R5 原版路径，不能随意改变原语义。

### 8.2 HTML/CSS 状态栏渲染

- 将解析出的 `html_template/css_asset/status_prompt` 与消息 `raw` 分离管理；显示层允许安全 HTML 子集，使用可靠的 HTML sanitizer，拒绝内联事件执行、危险 URI 和外部未批准资源。CSS 以当前 compat-root/Shadow DOM/隔离 frame 为作用域，防止改到顶栏、设置窗或其他会话。原有主题颜色 token 和 `?noCss=1` 救急入口保留。
- 若原卡把状态栏定义放在世界书里，它可能是**提示模型输出格式**，不是直接存在可渲染状态 UI：要先确认由什么正则生成/隐藏，再做真实 status renderer 适配。未满足依赖时显示“原始文本可见、状态栏待适配”。
- 生命周期：滚动、流式预览、编辑、重新生成、历史加载、换角色都能重算显示；卸载 CSS/HTML 后原始消息仍显示，不会被删除。

### 8.3 Variables/MVU

明确作用域：`session`, `card`, `script`, `message`（可扩展 `preset/global`，默认禁止跨故事/跨卡读取）。所有变量更新包含 `writeId`, `eventId`, `expectedRevision`, `sourceScriptId`, `namespace`；只对读得见的 namespace 提供脚本 API，权限单独校验。变量快照随会话回退、branch、重生恢复；不把 MVU 特定语法当通用 JSON 对象，也不在没有兼容实现时宣称 MVU 全面支持。角色卡里的变量定义/脚本扩展先识别和保留，再按约定 schema 逐版本适配。

### 8.4 媒体

播放器优先使用原生受控 UI adapter：会话内播放列表、播放暂停、进度、音量、循环、封面、音频来源/URL 许可；Windows/Android/iOS 的用户手势自动播放限制必须报告而不能标“播放失败已修复”。媒体失败只影响对应组件，绝不能影响文本回复；外部 URL 默认不静默向第三方泄露用户所在页面数据。脚本自行 fetch、访问浏览器媒体设备、麦克风或读文件均不自动批准。

### 8.5 R3 验收

同一角色消息的 `raw/canonical/prompt/rendered` 验证互不污染；包括状态栏带 HTML、正文隐藏但模型可见、模型看到但用户不可见、以及“用户看得到但模型不能看到”的区分。CSS 主题切换、手机视口、跨卡 CSS 隔离、变量回滚、播放按钮在环境许可下生效；浏览器刷新后显示和变量不丢失。

## 9. R4｜Tavern Helper/插件受限宿主：真正的高阶施工

### 9.1 插件类型区别

- A `character.extensions.tavern_helper.scripts[]`：内嵌 JS 源码，可能依赖 Tavern Helper 等特定环境；仅是资源，不代表已安装扩展。
- B 单文件 JSON 配置：可能是世界书/预设/Regex/Quick Replies/STscript；**JSON 本身不自动成为“插件”**。
- C ZIP/GitHub UI Extension：带 `manifest.json`、JS/CSS/assets，可能依赖别的扩展、网络和 UI DOM；要解析依赖和版本。
- D SillyTavern Server Plugin：Node.js 服务端插件，不适用浏览器沙箱，默认完全不在咪嘛馆执行；原版宿主 R5 需谨慎由用户显式安装。不得自动执行任意服务端脚本。

### 9.2 受控插件宿主；默认严格隔离

兼容运行环境采用隔离 iframe（独立/opaque origin、`sandbox=allow-scripts`，**禁止**与 `allow-same-origin` 搭配，使它能访问主页面同源）、受限 CSP（`default-src 'none'`、按需求许可资源/媒体；connect-src 默认 none）、可信宿主的消息代理和权限控制。每插件具唯一 frame、唯一可信启动 `MessagePort`/握手 nonce、sessionId、grantRevision、pluginHash、frame generation、requestId；拒绝非预期 origin/source、乱序、旧 frame 和越权消息。注意**sandbox iframe 本身不能完全隔离任意脚本所有副作用**，必须做 CSP、资源/外链导航、消息 RPC 和 DOM/UI 通道的组合限制。

页面主线程/父页面不能加载未知 JS 代码；不得通过去掉 sandbox、授予通用 `window.parent`/`window.top` DOM 访问权限或 `eval` 让脚本“能运行”。对已有脚本硬编码 `window.parent` 的行为，必须选：① 提供有证据的安全兼容 API/受控 UI frame；② 手工改造为派生脚本（原始字节不变，有 diff 和用户确认）；③ 转 R5 官方原生宿主。不能返回空数组假装 getMessages 完成，也不能所有 `eventOn` 都返回成功却不真正派发。

### 9.3 Capability-first Host API 合同

| 能力 | 初期 API/行为 | 必须的限制与真实验收 |
|---|---|---|
| `chat.read` | 只读当前 `sessionId` 的消息，结构化过滤/分页 | 不跨 session，数据一致、revision，原文/渲染视图区分 |
| `vars.read` / `vars.write` | read/write/replace namespace | CAS、授权、幂等、重生撤销/冲突 |
| `events.subscribe/emit` | chat mounted, new message, before/after generation, UI | 支持 unsubscribe、事件唯一 ID、订阅隔离、顺序与退出后清理 |
| `ui.mount` | 在专用 extension slot 添加按钮、浮窗/iframe、页面层 | 不能覆盖主输入/设置和别的卡；非跨源 DOM 写权限 |
| `media.control` | 受控播放器 / 资源列表 | 音频权限、浏览器限制、跨卡停止/清理 |
| `network.host` | 仅明确域名与路径的受控代理请求 | 严禁 `file://`、loopback/LAN SSRF、跨域密钥泄露；授权范围最小化 |
| `generation.request` | 可选异步附加生成 | 与主 Direct Reply 分队列、用量确认、不重复结算、不无限调用 |
| `chat.write` | 不默认提供；高风险高级权限 | 写入前要求本会话 revision、来源和确认机制；不可伪造主回复 |

API registry 有真实 shape、入参、返回值、错误代码、版本、权限要求和测试。未知 API 统一返回**明确的 `E_UNSUPPORTED_API` 并记录**，而非魔法 no-op。针对第三方典型 Tavern Helper、STscript/Quick Reply、MVU 分別定义 adapter：只有真正运行通过其用户可见效果才标 L4。

### 9.4 事件、生命周期、撤权、side effects

- 一个 `TavernSpeechTurn` 一位 settlement owner：用户请求先得到可信角色回复，插件可消费已提交事件但不得另作主回复权威。生成、解析、消息落库、展示、插件副作用分开。旧 attempt 不得覆盖新 attempt。
- EventBus 以 `eventId + subscriptionId + pluginHash + sessionId` 做去重与入场校验；持久副作用需 journal stable ID，重复启动、刷新、重试后不能重复发消息、重复加变量或重复播放。
- `unmount/disable/revoke/cross-session switch` 即停止该插件后续执行能力并使旧 grant revision 作废；旧消息或旧 frame 回调被忽略并诊断。卸载扩展**不删除**来源卡、角色消息、原始世界书和已保存用户变量快照，允许显式导出。
- 插件 UI 错误不得吞掉主回复；宿主失败对插件明确失败，不得把 null/[]/false 当作“没有事件/数据”；每个错误包含 `sessionId,turnId,pluginId,pluginVersion,eventId,stage,attempt,grantRevision,settlementState,error`（诊断需要遮蔽秘密）。

### 9.5 王爱英示范插件完成定义

原样解析并保留：13 条世界书（来源 8 开启）、9 条正则、3 个 Tavern Helper 脚本（其中 2 个标记启用）。

- 悬浮播放器：若原脚本依赖父页面，则先做能力 diff。受控播放器适配器能在当前剧情真正播放用户允许的资源，支持结束切卡后销毁，不等于原脚本 L4。若要 L4，需验证原按钮、播放列表、样式、事件和持久值行为。
- 虚拟手机：依赖消息事件、变量、父窗/顶层 DOM。验证其原卡的手机页面、消息读取、页面切换、变量更改、历史恢复在兼容宿主可见且行为一致；不具备时标记“R4 部分兼容/需要原版宿主”，不是删掉手机功能。
- 若原生 ST 独立宿主中也需要额外 Tavern Helper 扩展，R5 的导入向导必须提示并由用户按信任决定是否安装。

## 10. R5｜Windows 官方 SillyTavern sidecar：高保真退路，不伪装自研

### 10.1 一键引导与可选安装原则

- 自带 Windows `Install/Launch/Stop/Status/Repair/Rollback`（PowerShell + 可双击 `.cmd` 的稳定入口）工具；要求有网络/Node/npm/磁盘空间时提前预检，不得假设已安装某版本。安装到用户选的独立目录，例如 `E:\SillyTavern-Compat`（只是示例，**不是**用户必有路径），不覆盖主项目或别的 ST 安装。首次运行前显示预计目录/版本/下载来源与安全说明。
- 固定上游 GitHub 的 `tag+commit+SHA256` 到 `upstream-lock.json`，默认下载官方发布包/代码；下载失败保持原安装完整。不允许静默切非官方镜像或不明脚本；离线时明确提示并允许以后安装。脚本/可执行文件不可未经来源/校验即自动信任。
- 只监听 `127.0.0.1` 或严格 loopback；端口可配置，检测已占用且不杀别人的进程；认证与远程访问依据官方当前版本配置，不开放公网或防火墙规则，不把用户模型 API key 写进明文日志/启动命令。首次链接“已安装原生酒馆”路径也应可用。
- 所有变动使用 `manifest/rollback`：既有 config/data/extensions 不覆盖、不删除；升级前快照配置，检查上游兼容与 schema，再允许启用；重装/Repair 幂等。`Stop` 只结束本工具能证明 ownership 的进程，不能凭 PID 名称杀其他 Node。
- 浏览器主页面与 ST 是独立 origin/独立存储，不尝试用 iframe 越过 ST 的 CSP/frame-ancestors；若不允许嵌入就打开独立标签页，不加反向代理绕过浏览器保护。

### 10.2 侧车互通方式

**最初优先安全、清晰的手动快照导入导出**：咪嘛馆可以导出可供 ST 导入的角色卡/世界书/正则/预设/聊天快照；ST 可导出的格式再经 R1 检查器导入 Compat Session。双向字段映射附 diff，不共享 IndexedDB、不直接复制 ST 内部私有文件或浏览器会话。高级自动同步如果以后实现，必须有官方文档 API、明确认证/权限、版本契约以及冲突处理；不能根据 Web UI 内部请求猜接口、不能写入未公开 ST 数据库路径。

Sidecar 本身是原版玩法路径：官方宿主中的插件可能有任意高权限。SillyTavern 官方提示 UI 扩展可访问 DOM/context、Server Plugin 更高权限；用户应明确知道**一旦进入原版酒馆，安全边界由原版宿主及其安装扩展决定**。咪嘛馆 sandbox 不对该窗口提供安全保证。

### 10.3 R5 验收

Windows 无 Node/已有 Node、端口占用、断网、路径空格和中文、非管理员启动、重复安装、遗留安装升级、同一电脑已经有原版酒馆、重启/退出、日志/升级/回滚、浏览器不同源与 API key 隔离等矩阵。至少在真实 Windows 上启动官方 ST 并载入公开许可样本、独立世界书/Regex/已明确授权的扩展，完成一次可见互动与退出；不能只用 `npm` 成功退出码标记 R5 已通过。无法在施工环境测试 Windows 时交付 code-only 包 + **未实测**标记和实机验收步骤。

## 11. 依赖安装、许可证和上游版本策略

- ST 官方代码当前许可证按官方仓库确认：AGPL-3.0（本蓝图发现于官方 GitHub），若**复制/改造/打包**官方源码，需履行许可证及相关分发/源码开放义务；独立重写功能逻辑并不自动豁免第三方素材许可，分发 sidecar 也须核查条款。Tavern Helper、MVU 等第三方扩展的许可证逐一确认；未确认前不能把其整份 JS 直接夹进交包。
- 每个外部依赖必须有名称、精确版本/commit、来源仓库、许可、必要性、运行位置（浏览器或 sidecar）、hash、回滚方式；不把 GitHub `release/main` 浮动分支作为永久运行时契约。
- `upstream-lock.json` 每次只在明确升级时更新，伴随 golden fixtures 更新与差异报告。ST JS internals 不是稳定公共 SDK；不要承诺跨所有未来版本 100% 兼容。
- Source Capsule 的原始文本是用户提供的卡内容；不要在公开发布包里无许可复制/散发私人卡，含实际用户秘密的 sample 禁止写进程序/测试构建。工程测试 fixture 应用允许再分发的公开卡或自行构造的结构样本；王爱英样本可以在当前私有验收使用但**不得**打包进通用发布包。

## 12. 跨阶段一致性与错误分类合同

### 12.1 核心对象建议字段（非替代源 schema）

```ts
interface SourceCapsule { sourceId:string; sha256:string; filename:string; detectedFormats:string[]; rawBytesRef:string; parseStatus:'verified'|'degraded'|'invalid'; chunks:Array<{type:string,keyword:string,index:number,rawRef:string}>; importedAt:string; }
interface ResourceIR { resourceId:string; sourceId:string; jsonPointer:string; kind:string; host:string; hostVersion?:string; sourceEnabled:boolean; rawRef:string; normalizedPayload?:unknown; unknownFields:unknown; dependencies:string[]; issues:Array<{code:string,severity:string,path:string}>; }
interface CompatManifest { manifestId:string; sourceHashes:string[]; resourceRevisions:string[]; adapterLock:Record<string,string>; grantsRevision:number; readiness:'inspect_only'|'playable_verified'|'requires_original_host'; }
interface CompatSession { sessionId:string; sessionRevision:number; cardManifestId:string; runtimeVersion:string; adapterLock:Record<string,string>; mode:'native_compat'; promptProfile:string; activeBranchId:string; lastSettledTurnId?:string; }
interface CompatTurn { turnId:string; sessionId:string; baseRevision:number; attemptId:string; stage:string; rawInputRef:string; promptHash?:string; modelResponseHash?:string; canonicalMessageId?:string; settlement:'pending'|'committed'|'failed'|'aborted'; }
interface PluginGrant { grantId:string; pluginHash:string; sessionId:string; capabilities:string[]; approvedAt:string; revokedAt?:string; revision:number; }
```

实例仅是**规划接口**，工作猫要把它们设计成真实验证 schema（例如 JSON Schema / zod），有 decode/encode/迁移与业务级断言。不要只定义 TypeScript interface 然后把运行时 JSON 当可信对象。

### 12.2 明确失败类型

`E_SOURCE_CORRUPT`, `E_UNKNOWN_SCHEMA`, `E_CHUNK_CONFLICT`, `E_ZIP_PATH_TRAVERSAL`, `E_DECOMPRESS_BUDGET`, `E_RESOURCE_SEMANTIC_GAP`, `E_ADAPTER_VERSION_MISMATCH`, `E_IMPORT_CONFLICT`, `E_CANONICAL_CONFLICT`, `E_STORE_UNVERIFIED`, `E_PROMPT_POSITION_UNSUPPORTED`, `E_WORLDINFO_EVAL`, `E_REGEX_PHASE_UNSUPPORTED`, `E_REGEX_BUDGET`, `E_PLUGIN_PERMISSION_DENIED`, `E_PLUGIN_API_UNSUPPORTED`, `E_PLUGIN_STALE_FRAME`, `E_SIDE_CAR_UNAVAILABLE`。错误中带根源状态、对应阶段、被阻断的用户能力及安全恢复操作；被阻断资源绝不能在 UI 里显示“已启用并运行”。

## 13. 一次性交包的施工工序与依赖图（不得打乱）

```text
前置 P0：真实最新源码复核 + 冻结基线 + 样本与许可证清单
  ↓
R1-A 新兼容库、来源包、格式识别、资源树、事务/回滚/备份
  ↓  Gate 1 数据可靠性、old-mode regression
R2-A 兼容 Session、PromptSegments、WorldInfo 引擎、ProviderAdapter
  ↓  Gate 2 与 pinned ST 实际 prompt/worldbook 对照
R3-A Regex 阶段、HTML/CSS 安全渲染、VariableStore、媒体基建
  ↓  Gate 3 raw/prompt/rendered 分离与演出真实生效
R4-A 插件清单/依赖/授权、沙箱 RPC、TavernHelper 特定 API、受控媒体
  ↓  Gate 4 可运行插件的真实用户可见行为、撤权、注入安全
R5-A Windows 原版酒馆可选安装与生命周期、导入导出路径
  ↓  Gate 5 Windows sidecar 独立启停/迁移/真实扩展
最终 G0：原生基线无退化、全量数据完整性、影响面反查、完整回滚
```

全部环节允许内部拆成小 commit 与原子补丁，**最终提交一个可独立安装的完整总包**；某 Gate 不通过，不能跳过继续宣布“全做完”，而应完成真正根因修复后重新验证受影响 Gate。若环境缺少真实模型/官方 sidecar/Windows，明确列出静态验证与需要用户后续做的验收，而非宣称完整 PASS。

本方案允许“一次施工覆盖 R1–R5”，但**不等于**能保证所有未知酒馆扩展脚本在咪嘛馆自研容器内一模一样。我们承诺的是“来源数据不丢、已支持语义可核验运行、插件有真实权限/功能报告、不支持时可选择原版宿主”。这才是兼容最大化而不牺牲原生咪嘛馆可靠性与用户安全的实现方式。
